# cut-stack — разбиение на эпики

## Обзор

Документ фиксирует полный инвентарь требований и дальнейшее разбиение на эпики и истории: требования из PRD, UX-спецификации и архитектуры превращаются в исполнимые истории с критериями приёмки.

## Requirements Inventory

### Functional Requirements

```
FR1: Владелец мастерской задаёт пресеты листов, kerf, trim и зазоров фасада.
FR2: Владелец мастерской создаёт, открывает, сохраняет и копирует проекты.
FR3: Владелец мастерской применяет профиль мастерской к новому проекту без повторного ввода базовых параметров.
FR4: Владелец мастерской задаёт габариты напольного шкафа с полками, задником и 1–2 фасадами.
FR5: Владелец мастерской задаёт габариты тумбы с опциональной выдвижной секцией в рамках фурнитуры v1.
FR6: Владелец мастерской собирает линейную гардеробную из нескольких секций с индивидуальными размерами.
FR7: Владелец мастерской собирает L-гардеробную из двух плеч под 90° с согласованным угловым стыком.
FR8: Владелец мастерской назначает фасады только на выбранные секции модуля.
FR9: Система ведёт чистовые размеры деталей и размеры заготовок под кромку как отдельные величины.
FR10: Владелец мастерской назначает кромку 0,4 мм и 2 мм по сторонам детали с влиянием на заготовку.
FR11: Система учитывает толщину панели из пресета материала в деталировке.
FR12: Система учитывает направление декора при раскладке, где применимо к материалу.
FR13: Система строит guillotine-раскладку под ручную пилу для выбранного формата листа.
FR14: Владелец мастерской выбирает формат листа из согласованных пресетов v1.
FR15: Система формирует 2–3 варианта раскладки или поддерживает повторный прогон с изменёнными параметрами.
FR16: Владелец мастерской вручную корректирует карту раскроя с сохранением исполнимости guillotine.
FR17: Система связывает каждую деталь с листом и позицией на листе в деталировке.
FR18: Владелец мастерской назначает накладные петли на фасад в рамках сценария v1.
FR19: Система рассчитывает количество петель и отверстия по выбранному семейству шаблона.
FR20: Владелец мастерской конфигурирует один выдвижной ящик по внутреннему проёму тумбы.
FR21: Система рассчитывает отверстия направляющей по согласованному шаблону v1.
FR22: Система формирует перечень фурнитуры по активным сценариям v1 без полного каталога производителей.
FR23: Владелец мастерской просматривает 3D-сборку корпуса, полок, задника и фасадов.
FR24: Владелец мастерской проверяет в 3D проём, зазоры фасадов и стыки, включая L-гардеробную.
FR25: Система отображает зоны фурнитуры в 3D в объёме, достаточном для проверки, без фотореалистичного рендера.
FR26: Владелец мастерской экспортирует деталировку и привязку к листу в CSV v1.
FR27: Владелец мастерской экспортирует карту раскроя для цеха в PDF.
FR28: Экспорт отражает слой размеров, предназначенный для пилы, отдельно от чистовых обозначений.
FR29: Система сопровождает экспорт дисклеймером об ответственности производителя за соответствие изделию.
FR30: Система не требует внешних интеграций с CAD, ERP, ЧПУ и учётными системами для прохождения основного цикла v1.
```

### NonFunctional Requirements

```
NFR1: На эталонных проектах v1 (шкаф, тумба, L-гардеробная) UI остаётся отзывчивым при навигации и правках параметров.
NFR2: Пересчёт guillotine на полном составе деталей v1 завершается с явным индикатором прогресса; основной поток не блокируется дольше допустимого порога, зафиксированного в чек-листе приёмки.
NFR3: 3D-сборка эталонных корпусов допускает интерактивный осмотр без заметных фризов на целевом desktop-браузере.
NFR4: В v1 нет multi-tenant и обязательной аутентификации; проекты не публикуются в общий доступ по умолчанию.
NFR5: При любом сетевом хранении или синхронизации передача данных — только по TLS; ПДн заказчиков не собираются без явного scope.
NFR6: Экспортированные CSV/PDF не содержат скрытых служебных данных вне согласованной схемы v1.
NFR7: Сохранённые проекты и профиль мастерской восстанавливаются после перезапуска приложения без потери согласованного набора полей v1.
NFR8: Сбой пересчёта раскроя не повреждает сохранённый проект; пользователь может повторить расчёт или откатиться к последнему сохранённому состоянию карты.
NFR9: Формы ввода параметров и основные подписи читаемы при стандартном масштабе desktop; контраст карты раскроя в PDF достаточен для чтения у пилы.
NFR10: Полное соответствие WCAG AA для публичного маркетинга в v1 не требуется.
NFR11: Внешние интеграции (CAD, ERP, ЧПУ, 1С, БАЗИС) в v1 не входят в обязательные NFR.
NFR12: CSV v1 остаётся стабильной по полям между минорными релизами v1; изменения схемы версионируются явно.
```

### Additional Requirements

```
- Epic 1 / первая implementation story: не создавать проект из CLI — расширять существующий монорепозиторий cut-stack (Turborepo + pnpm + Next.js 16); точка входа `pnpm install` и `pnpm dev`.
- Персистентность v1: браузер (IndexedDB или тонкая обёртка), явное поле версии схемы документа и миграции read/write; несовместимая версия — явный путь миграции или «создать проект заново» без тихой порчи данных.
- Граница домена: расчёты и правила размеров/раскроя — в `packages/*` (план: `cut-stack-domain`, `cut-stack-nesting`, `cut-stack-hardware`, `cut-stack-persistence`, `cut-stack-export`); UI и оркестрация — в `apps/clients/web`.
- Первый приоритет реализации (handoff): каркас `packages/cut-stack-domain` с публичными типами и инвариантами размеров/листа; затем `cut-stack-persistence` с версией схемы и миграцией.
- Экспорт: стабильная CSV v1 и PDF с явным слоем «на пилу»; дисклеймер в выводе; колонки CSV — snake_case; внутренние JSON-снимки — camelCase.
- Коммуникация слоёв: Server Actions и/или прямые импорты доменных пакетов; Route Handlers (`/api/...`, kebab-case) — точечно (например PDF); JSON-ошибки `{ "error": { "code", "message" } }` без утечки стека в прод (когда появится прод).
- Изоляция тяжёлого nesting от UI: Web Worker или отложенный batch с индикатором прогресса (конкретный механизм — в story; принцип зафиксирован).
- Ошибки домена: Result / discriminated union; UI не перезаписывает сохранённый проект при ошибке пересчёта; откат к последнему известному хорошему состоянию карты (политика в story).
- Node.js: выровнять `engines` в корневом `package.json` с Next.js 16 (ориентир ≥ 20.9) при введении CI/деплоя.
- Важный gap: оформить отдельную спецификацию полей CSV v1 (таблица колонок, разделитель, десятичный формат) и ссылку из `cut-stack-export`.
- Важный gap: зафиксировать выбор Web Worker vs main-thread async для nesting в первой story перфоманса.
- Аутентификация и multi-tenant не проектировать в модели данных v1; при sync — только TLS и минимизация ПДн.
- Паттерны для агентов: не дублировать kerf/trim/кромку в UI; не добавлять auth, multi-tenant и внешние интеграции без явного изменения architecture/PRD; BMad-артефакты только в `_bmad-output/`.
- Тесты: runner не зафиксирован; при появлении — `*.test.ts` рядом с модулем в пакете; CI минимум `lint` и `check-types` до появления test gate.
```

### UX Design Requirements

```
UX-DR1: Инициализировать shadcn/ui CLI в `apps/clients/web` (путь компонентов `src/components/ui` или согласованный alias); совместимость с Tailwind v4 и React 19 — по официальной документации на момент установки.
UX-DR2: Согласовать CSS variables shadcn (`--background`, `--foreground`, `--muted`, `--border`, `--primary`, `--destructive`, `--ring` и др.) с существующим `@theme inline` / Geist в `globals.css`; одна палитра светлой темы v1.
UX-DR3: Зафиксировать правило сосуществования `@repo/ui` и shadcn для v1: новые фичи cut-stack на shadcn в web; `@repo/ui` — демо/постепенные re-export обёрток (вариант A из спеки).
UX-DR4: Реализовать компонент `DimensionLayerSwitch` — единый переключатель трёх слоёв размеров (чистовой / заготовка под кромку / на пилу) на табах Детали и Раскрой и в превью экспорта; доступность radiogroup, фокус, Tooltip; опционально disabled при небезопасном пересчёте.
UX-DR5: Реализовать `ProjectAppShell` — sidebar («Проекты», «Мастерская») + project chrome + горизонтальные табы проекта (Параметры / 3D / Детали / Раскрой / Фурнитура / Экспорт или объединение по реализации); layout в Next.js App Router.
UX-DR6: Реализовать `ExportDialog` — единый `Dialog` с превью полей CSV/PDF, дисклеймером FR29 и явными действиями экспорта (не три отдельных «магических» мастера).
UX-DR7: Реализовать `SheetCutMap` — 2D карта листа guillotine (canvas или SVG): нумерация резов, grain, варианты A/B/C, панель zoom/fit/«сброс к авто»; опциональный тёплый фон зоны карты (направление 4); состояния пусто/загрузка/правка/ошибка валидации.
UX-DR8: Реализовать `NestingVariantCards` — 2–3 карточки вариантов на `Card` с метриками (листов, отход) и выбором активного варианта; skeleton/disabled при пересчёте; empty state.
UX-DR9: Реализовать `Viewport3DPanel` — оболочка вокруг 3D-сцены (`Card`/bordered), тулбар вида, состояния загрузки/ошибки/конфликта геометрии с callout из домена.
UX-DR10: Установить приоритетный набор shadcn-компонентов: `Button`, `Input`, `Label`, `Select`, `Checkbox`, `Tabs`, `Table`, `Dialog`, `Sheet`, `DropdownMenu`, `Tooltip`, `Progress`, `Separator`, `Card`, `Alert`, `ScrollArea`; затем `Form` (react-hook-form + zod) для мастерской и параметров корпуса.
UX-DR11: Типографика: Geist Sans для UI; Geist Mono для мм, кодов деталей, превью CSV; зона карты — на ступень крупнее базового body (`data-density="shop-floor"` или классы).
UX-DR12: Иерархия кнопок: один primary на экран/модалку; destructive только с `Dialog`; toolbar карты/3D — ghost/outline + Tooltip.
UX-DR13: Обратная связь: `Progress`/индетерминированный индикатор для nesting; `Alert` для ошибок расчёта с действиями «Повторить»; предупреждения раскроя — отдельный визуальный стиль от error; короткий toast только для проверяемых действий («Проект сохранён»).
UX-DR14: Формы: одна колонка, группировка `Card`; валидация onBlur/onSubmit для размеров в мм; disabled с явной причиной в Tooltip; zod-схемы синхронны с доменом.
UX-DR15: Навигация: сохранение активной вкладки в URL query (`?tab=cut`) по возможности; sidebar на `lg`; ниже `lg` — упрощённый layout; sidebar → `Sheet`/overlay при нехватке ширины.
UX-DR16: Responsive: desktop-first (`min-width`); ключевые пороги Tailwind `lg` (split), ниже — стек/табы; мобильный <768 — не обещать полный цикл v1 (заглушка или read-only — решение в реализации).
UX-DR17: Доступность: WCAG 2.1 AA для основного UI (формы, навигация, модалки, таблица вне canvas-only потоков); контраст линий карты максимально близко к AA; видимый `--ring`; ловушка фокуса в Dialog/Sheet; `aria-busy`/live region для длительного nesting; не полагаться только на цвет на карте.
UX-DR18: Альтернативный layout вкладки «Раскрой»: карта снизу на всю ширину на широком breakpoint (направление 5) — опционально, не единственный каркас.
UX-DR19: Копирование проекта: `DropdownMenu` у строки проекта; имя копии по умолчанию явное; подтверждение не требуется (как в спеке).
UX-DR20: Ручная правка карты: drag-and-drop или пошаговый редактор — по реализации; явная «Сбросить к авто»; валидация guillotine на месте.
UX-DR21: Локализация UI: русский язык; согласование отображения десятичной запятой в UI с правилами CSV v1 отдельно.
UX-DR22: Референс `_bmad-output/planning-artifacts/ux-design-directions.html` — только для обсуждения; финальный UI по выбранному направлению 1 (+ тёплый фон canvas из направления 4 при необходимости).
```

## Epic List

### Epic 1: Пресеты мастерской и проекты

После эпика владелец мастерской задаёт **пресеты листов, kerf, trim и зазоры фасадов**, ведёт **проекты** (создать, открыть, сохранить, копировать) и **подтягивает профиль** в новый заказ без повторного ввода базовых параметров.

**FRs covered:** FR1, FR2, FR3

### Epic 2: Типовые корпуса — от шкафа до L-гардеробной

После эпика пользователь задаёт **типовые корпуса** (шкаф, тумба, линейная и L-гардеробная под 90°) и **назначает фасады** только на выбранные секции.

**FRs covered:** FR4, FR5, FR6, FR7, FR8

### Epic 3: 3D-проверка сборки и стыков

После эпика пользователь **просматривает 3D-сборку**, проверяет **проём, зазоры и стыки** (включая L) и видит **зоны фурнитуры** в объёме, достаточном для проверки.

**FRs covered:** FR23, FR24, FR25

### Epic 4: Деталировка — два слоя размеров, кромка, материал, grain

После эпика система ведёт **чистовые размеры и заготовки под кромку**, учитывает **кромку 0,4/2 мм**, **толщину панели** из пресета и **grain/декор** в раскладке.

**FRs covered:** FR9, FR10, FR11, FR12

### Epic 5: Guillotine-раскрой с вариантами и ручной правкой

После эпика пользователь получает **guillotine-раскладку** на выбранном **пресете листа**, **2–3 варианта** или повторный прогон, может **вручную править карту** и видит **привязку каждой детали к листу и позиции**.

**FRs covered:** FR13, FR14, FR15, FR16, FR17

### Epic 6: Фурнитура сценариев v1

После эпика пользователь назначает **накладные петли** и **один выдвижной ящик**, получает **отверстия по шаблонам** и **перечень фурнитуры** без полного каталога производителей.

**FRs covered:** FR18, FR19, FR20, FR21, FR22

### Epic 7: Цеховой пакет — CSV v1 и PDF

После эпика пользователь выгружает **CSV v1** и **PDF** с явным слоем **«на пилу»**, **дисклеймером** и проходит **основной цикл v1 без обязательных внешних интеграций**.

**FRs covered:** FR26, FR27, FR28, FR29, FR30

## Epic 1: Пресеты мастерской и проекты

Владелец мастерской настраивает **цеховые пресеты** и ведёт **проекты** в одном приложении: данные **сохраняются локально**, после перезапуска восстанавливаются, новый заказ начинается с **уже заданных** kerf/trim/листа.

### Story 1.1: Каркас приложения, shadcn и навигация «Проекты / Мастерская»

As a владелец мастерской,
I want открыть приложение с понятной навигацией между списком проектов и настройками мастерской,
So that быстро переключаться между заказами и пресетами без потери контекста.

**Acceptance Criteria:**

**Given** пустой или частично инициализированный клиент в `apps/clients/web`
**When** пользователь открывает корневой маршрут приложения
**Then** отображается `ProjectAppShell` (боковая навигация: «Проекты», «Мастерская») согласно UX-DR5 и направлению 1 из UX-спеки
**And** в проект добавлены базовые shadcn-компоненты (UX-DR1) и согласованы CSS variables с `globals.css` (UX-DR2), зафиксировано правило сосуществования с `@repo/ui` (UX-DR3)
**And** на ширинах ниже `lg` боковая навигация может схлопываться в `Sheet`/оверлей без потери доступа к разделам (UX-DR15, UX-DR16)
